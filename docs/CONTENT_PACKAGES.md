# Signed curriculum package foundation
Shared strict data schema is used by the admin validation CLI and the browser. Runtime capability map derives from implemented activity engine versions. The package format uses a bounded exact UTF-8 JSON payload, canonical base64url, P-256 ECDSA/SHA-256 raw 64-byte signature, signed curriculum ID, release ID, version and monotonic delivery sequence. Verification requires explicitly pinned public JWKs, validates signature before parsing payload, checks curriculum ID and sequence floor, and refuses unsupported activity versions. No executable content, no keys from packages. Offline verification code is bundled in Android/web cache. Admin signing primitive and cross-language CI use ephemeral test keys only.
Not a delivery system yet: no trusted production key, key rotation/revocation, persistent sequence floor, download route, install/storage UI or automatic activation. The signature does not by itself prove editorial approval; future exporter must authorize publication and retrieve the active approved release from the database, allocate a durable monotonic delivery sequence (including rollback), and sign only that release. Current signing primitive is internal and not exposed via HTTP. Do not enable content delivery before pinned keys, atomic install, replay prevention, compatibility manifests, and learner runtime integration are tested. Older WebViews without WebCrypto must fail closed.
Staging export candidate: permission-gated /api/draft/export, expected active release, lock and monotonic DB sequence, no arbitrary signing input. Explicit LOLO_ADMIN_STAGING_EXPORT=true and private P-256 PEM outside repository plus LOLO_ADMIN_SIGNING_KEY_ID required on trusted loopback operator server. No key included. The client now has IndexedDB staging primitives: one atomic record containing signed envelope/sequence, concurrent read/write serialized by transaction; verify again on read, reject stale sequence and conflicting payload at same sequence, no learner progress writes. No public download, trust configuration or learner activation yet. Device storage deletion/local tampering can reset the replay floor; key lifecycle and durable delivery state remain deployment requirements. Tests use synthetic ephemeral keys and actual Chromium IndexedDB.
