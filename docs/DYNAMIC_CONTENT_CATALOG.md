# Dynamic signed curriculum distribution
New optional independent PostgreSQL catalog contains signed public educational envelopes only. No account or student data, no admin credentials and no signing private key in the student deployment. Reader uses an explicit SELECT-only connection and verified TLS; writer credential never belongs in Vercel student environment. Runtime refuses mixed known family/admin schemas and same configured DSN strings. Operator must verify actual DB/role separation, not just string inequality. Apply database/content-catalog/001_catalog.sql to a new dedicated database only; grant SELECT to reader, SELECT/INSERT/UPDATE to separate operator role. Use verified TLS for both. No changes to main Neon bootstrap.
After owner/reviewer approve an active curriculum and trusted operator exports the signed package, enroll a reviewed public JWK in content-trust.js and release the build once. Keep private key outside Git and Vercel. Trusted operator can then publish reviewed envelopes via scripts/publish_content.py with --expected-sequence N and explicit confirmation. The script uses the exact student verifier and build-pinned keys; no arbitrary signing. Monotonic compare-and-swap, serialized concurrent updates, idempotent retry, bounded catalog and rollback by newly signed higher sequence. Existing cached versions remain usable offline; content is not removed remotely. To serve dynamically, set LOLO_CONTENT_CATALOG_BACKEND=database, LOLO_CONTENT_CATALOG_DATABASE_URL to the dedicated reader and LOLO_CONTENT_DELIVERY_ENABLED=true after approval. File backend remains backward compatible; no fallback to file if DB is unavailable. New publications then require neither a new APK nor a Vercel build as long as the installed engine and trust key remain compatible.
Current status: code candidate and disposable database tests only. No real keys, schema migration, credentials, catalog rows, flags, deployment or public publication performed. Owner panel publishing button and private operator export UI still need integration. Shared cross-instance catalog rate limiting, role grants, recovery/backup, key rotation and actual device tests must be verified before activation.
